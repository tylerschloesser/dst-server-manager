# Generating a brand-new DST world from the web UI

Research date: 2026-09-19. Scope: feasibility and cost of adding "create a new
world" (not just "start an existing world") to the on-demand DST server webapp.
Claims marked **[doc]** (official/documented), **[forum]** (community report,
unverified), or **[inference]** (my reasoning, not sourced).

Ground truth for section 1–2 came from inspecting the file *names* and
non-secret key/value pairs inside Tyler's real, working cluster archive
(`~/Downloads/dst-tylerni2026.zip`, cluster `TylerNi2026`) in a scratch temp
dir that was deleted afterward. `cluster_token.txt` and the `cluster_password`
value were never read or printed. That inspection is called **[zip]** below —
it's the strongest evidence available because it's an actual server Klei's
client generated and DST has been happily running, not a guide's guess.

## 1. Minimum file set for a fresh cluster (complete templates)

A cluster is just a directory tree; the dedicated server decides "new world"
vs "load" per-shard based on whether that shard's `save/` directory contains
a valid save (see §3). The files below are everything needed — no `save/`
directory should be created for a brand-new world; the server creates it.

```
<ClusterName>/
  cluster.ini
  cluster_token.txt        (shared Klei token — copied in at boot, per v1 design)
  adminlist.txt            (optional)
  Master/
    server.ini
    leveldataoverride.lua  (optional but recommended — see §2)
  Caves/                   (optional — omit entirely for forest-only worlds)
    server.ini
    leveldataoverride.lua  (required in practice — see §2)
```

### cluster.ini (complete, both Master+Caves)

Verified against Tyler's real, running cluster **[zip]**, cross-checked
against the community-standard template shipped in
[mathielo/dst-dedicated-server](https://github.com/mathielo/dst-dedicated-server/blob/main/DSTClusterConfig/cluster.ini)
(a widely-forked Docker packaging of the same config, itself derived from the
Klei forum guide) **[doc/forum]** and the
[Klei Dedicated Server Settings Guide](https://kleiforums.com/forums/topic/64552-dedicated-server-settings-guide/)
(page itself returns HTTP 403 to automated fetch; content corroborated via
search snippets and the two community re-hosts above) **[doc, secondhand]**.

```ini
[GAMEPLAY]
; survival | endless | wilderness
game_mode = survival
; 1..64
max_players = 6
; true | false
pvp = false
; true | false — pause the world sim while no players are connected
pause_when_empty = true
; true | false — optional, controls in-game vote-kick UI
vote_kick_enabled = false

[NETWORK]
cluster_name = My World
cluster_description =
; secret — never commit to a public repo; see §6 for where this comes from
cluster_password = <injected from SSM at boot>
; cooperative | competitive | social | madness — cosmetic "Playstyle" label
; shown in the server browser as of the 2022 world-settings overhaul (see §4)
cluster_intention = cooperative
lan_only_cluster = false
offline_cluster = false
cluster_language = en
autosaver_enabled = true

[MISC]
console_enabled = true
; number of rollback-able save snapshots to retain
max_snapshots = 6

[SHARD]
shard_enabled = true
bind_ip = 127.0.0.1
master_ip = 127.0.0.1
master_port = 10888
; secret-ish — shared key Master/Caves processes use to authenticate to each
; other over loopback; does not need to be a Klei credential, just a random
; string unique-ish per cluster
cluster_key = CHANGE_ME_RANDOM_STRING

[STEAM]
steam_group_only = false
steam_group_id = 0
steam_group_admins = false
```

Notes:
- `tick_rate` is a valid, documented `[NETWORK]` key (10/15/30/60, default 15)
  **[doc]** but Tyler's real, working cluster.ini omits it entirely and runs
  fine — it is **optional, not required** **[zip + inference]**.
- `vote_kick_enabled` appears in Tyler's real file; some guides call the same
  toggle `enable_vote_kick` or `vote_enabled` in older examples — the key name
  has drifted across DST versions/guides. **[forum, low confidence — pick the
  name from a cluster.ini actually generated by the current game client
  rather than an old guide if this ever breaks]**.
- `cluster_key` under `[SHARD]` is **not** the Klei account token. It is a
  cluster-communication secret Master and Caves use to talk to each other
  locally. It does not need to be secret from AWS (it never leaves the
  instance / VPC) but should not be a guessable constant if defense-in-depth
  matters at all. **[inference]**

Verified against Tyler's real cluster **[zip]**.

```ini

[SHARD]

name = Caves
id = 40987672

[ACCOUNT]
encode_user_path = true

[STEAM]
master_server_port = 27017

```

`id` under `Caves/server.ini [SHARD]` is a shard identifier (looked like an
arbitrary-looking numeric string in the real file). **[zip, meaning
inferred]** — community templates (e.g. mathielo's) omit `id` for Caves
entirely and it still works, so it appears to be optional/auto-assignable,
not something a "new world" generator must invent carefully. **[forum,
medium confidence]**

Ports: Master uses `10999`/`27016`/`8766`, Caves uses `10998`/`27017`/`8767`
in Tyler's real setup — one fixed pair of port-sets per shard role. Since
only one world runs at a time (§6), a new-world generator does **not** need
a port-allocation scheme; it can hardcode these same two port-sets for every
world.

## 2. World settings: worldgenoverride.lua vs leveldataoverride.lua

**`leveldataoverride.lua` is what the current (2026) game actually writes and
reads, and is what should be treated as canonical.** Tyler's real, live
cluster contains only `leveldataoverride.lua` in both `Master/` and `Caves/`
— no `worldgenoverride.lua` is present anywhere **[zip]**. This matches the
[DST Wiki dedicated servers guide](https://dontstarve.wiki.gg/wiki/Guides/Don%E2%80%99t_Starve_Together_Dedicated_Servers):
"`worldgenoverride.lua` is the nicer, more human-readable file intended to be
used by server admins. `leveldataoverride.lua` is used internally by the DST
client to store world settings... At least one needs to be specified. If both
files are present, the contents of `leveldataoverride.lua` will override that
of `worldgenoverride.lua`." **[doc]**

Practical read: `worldgenoverride.lua` is a legacy/manual authoring format
still accepted by the server, but the modern flow (the in-client "World
Settings" customization screen, and what actually ships in a
server-generated cluster) produces `leveldataoverride.lua` directly. **A new
cluster generator should write `leveldataoverride.lua` directly** rather than
the older, sparser `worldgenoverride.lua` format — it's a strict superset and
is what the real game produces. **[inference from zip, medium-high
confidence]**

### Minimal correct Master/leveldataoverride.lua (default Forest, SURVIVAL_TOGETHER)

Tyler's real file is much longer (it enumerates ~150 `overrides` keys, all
set to `"default"`, because that's what the game client writes when you
don't touch any sliders). A hand-authored generator does **not** need to
enumerate every key — DST fills in unset override keys with the preset's
defaults. The [GitHub issue on yeet-zone/docker-dontstarvetogether #97](https://github.com/yeet-zone/docker-dontstarvetogether/issues/97)
confirms the file format requires five top-level fields: `id`, `location`,
`name`, `desc`, `overrides` **[forum, corroborated by zip's real file having
exactly these fields plus some cosmetic/version metadata]**. Minimal viable
version:

```lua
return {
  id = "SURVIVAL_TOGETHER",
  location = "forest",
  name = "Survival",
  desc = "The standard Don't Starve experience.",
  overrides = {},
}
```

### Minimal correct Caves/leveldataoverride.lua (default Caves, DST_CAVE)

```lua
return {
  id = "DST_CAVE",
  location = "cave",
  name = "The Caves",
  desc = "Delve into the caves... together!",
  overrides = {},
}
```

These minimal forms are an **[inference]** from combining the zip's real
(much more verbose) files with the GitHub issue's statement of required
fields; they have not been independently boot-tested by this research pass.
Recommendation: **do not hand-round-trip these** — instead, generate a real
world once in-client (or via the existing zip's Master/Caves files as a
byte-for-byte starting template) and treat that as the "default Forest" /
"default Caves" seed content, only patching `overrides{}` keys for anything
the UI actually exposes (§4). This avoids needing to prove the minimal form
boots correctly.

### What happens if the file is omitted

- **On Master**: not independently confirmed by an authoritative source in
  this pass, but the wiki's phrasing ("at least one needs to be specified")
  implies Master generates *some* default forest even with neither file
  present, since a bare install is expected to boot into a fresh Forest
  world out of the box. **[inference, low-medium confidence — did not find a
  source that boots a Master shard with zero override file and observes the
  result]**.
- **On Caves — CONFIRMED this is a real, common failure mode**: a Caves
  shard with no (or misconfigured) cave preset generates as a second Forest
  rather than as caves. Steam Community thread
  ["dedicated server - cave is no cave"](https://steamcommunity.com/app/322330/discussions/0/3377008022028484831/):
  a user's sinkhole led to "another world" instead of the caves shard; the
  fix was "forgotten to set up the DST_CAVE preset setting for the slave
  server's worldgenoverride.lua" **[forum]**. The GitHub issue above
  independently confirms the newer `leveldataoverride.lua` format made this
  worse, not better, by adding required fields (`location`, etc.) beyond
  just an `id`/preset name, meaning a naive port from old `WORLD_PRESET`-only
  tooling silently produces a broken (forest) Caves shard **[forum/doc]**.
  **Actionable conclusion: a world generator MUST always write a correct,
  complete Caves `leveldataoverride.lua` with `location = "cave"` whenever a
  cave shard is created — there is no safe "omit it and get a sane default"
  path for Caves.**

## 3. First-boot world generation time and failure modes

- Forum reports vary widely: one Klei forum poster reported worldgen "used
  to take 2-5 minutes" but on a later occasion "took about 25 minutes"
  ([World Generation Speed](https://kleiforums.com/forums/topic/145080-world-generation-speed/),
  content only accessible via search snippet, direct fetch returned 403)
  **[forum, low confidence on exact numbers, but the order-of-magnitude
  "single-digit to ~20-30 minutes" range recurs across similar threads]**.
  A Steam Community thread titled "World Generation taking forever" exists
  with the same theme (title only retrieved, not opened) **[forum, title
  only]**.
- **Practical guidance for this project: budget several minutes for
  first-boot generation, and treat >20-30 minutes without the server
  reporting ready as a probable hang, not "still working."** **[inference]**
- **Failure mode — no worldgen retry loop found in an authoritative source,
  but one that is directly analogous and load-bearing was found**: a
  malformed/incomplete `leveldataoverride.lua` for Caves doesn't produce an
  error — it silently produces a second Forest (§2). This means monitoring
  "did the process exit 0 / is the port listening" is **not sufficient** to
  detect a broken new-world generation; the ops/monitoring design should
  also sanity-check the generated `Caves/save/` (or the shard's own logs)
  actually reports `location = cave` type content, or accept the risk for
  v1. **[inference]**
- The one common operational gotcha repeatedly mentioned across guides
  (XGamingServer's world-generation doc, several server-host KBs): a
  worldgen override file "only applies when the world is first generated" —
  editing it after a `save/` already exists does nothing until the save is
  deleted **[doc/forum, high confidence, repeated across multiple
  independent sources]**. This is directly relevant: it confirms the
  server's rule is genuinely "presence of `save/` decides generate-vs-load,"
  supporting the architecture in §6.

## 4. Game modes / presets worth exposing in a "new world" form

Klei's 2022 "World Settings" overhaul **[doc/forum, corroborated by multiple
current hosting-KB pages]**:
- Replaced/absorbed the old three `game_mode` values (`survival`, `endless`,
  `wilderness`) into a single "World Settings" system with **Playstyle**
  presets shown in the server browser, generated from the same underlying
  `game_mode` + override sliders. `game_mode` in `cluster.ini` is still a
  real, respected key (`survival | endless | wilderness`)
  ([Nodecraft: Change Game Mode](https://cybrancee.com/learn/knowledge-base/how-to-change-the-game-mode-survival-endless-wilderness-on-your-dont-starve-together-server/)).
- **Survival** (default): world resets to a fresh generation if the whole
  party dies; ghosts have a limited revival window. **Endless**: never
  resets; players can self-revive at the portal with a max-health penalty.
  **Wilderness**: random spawn points, no forced cooperation, never resets.
  **Relaxed** (a *preset*, layered via `leveldataoverride.lua`/
  `worldgenoverride.lua` overrides rather than a `game_mode` value): no
  starve/freeze/overheat/darkness death, -35% damage taken, fewer hound
  waves, ghosts revive at the Florid Postern, no world reset
  ([servers4gamers: playstyle change](https://servers4gamers.com/blog/how-to-change-playstyle-on-a-dont-starve-together-server/))
  **[forum]**.
- **"Lights Out"**: an infinite-night variant achievable via day/night
  override sliders in the level-data overrides, not a first-class
  `game_mode` value **[forum, low confidence — surfaced only as a
  community-built override recipe, not a named preset key]**.
- `cluster_intention` (`cooperative | competitive | social | madness`) is a
  separate, purely cosmetic "Playstyle" label shown in the server browser —
  distinct from `game_mode` **[doc, confirmed in real cluster.ini and
  community templates]**.

**Smallest sensible "new world" form** (my recommendation, **[inference]**):
- Name (`cluster_name`) — free text, needs sanitization (§7).
- Description (`cluster_description`) — free text, optional, needs
  sanitization.
- Max players (`max_players`) — integer, default 6, cap at something sane
  (e.g. 16) given this is a 6-friend allowlist use case.
- Game mode — dropdown: Survival (default) / Endless / Wilderness. Skip
  Relaxed/Lights Out/madness-intention for v1 — they require hand-authored
  override tables, not a single key flip, and add real testing surface for
  a feature already flagged "design-for and defer" (§7).
- Caves — checkbox, "most will have caves" per Tyler's own requirement, so
  default checked ON.
- Password — do **not** expose per-world; see §6 (one shared cluster
  password/token model is simplest and matches "only one world runs at a
  time").

## 5. adminlist.txt

- Location: cluster root, alongside `cluster.ini` (confirmed in Tyler's real
  cluster: `TylerNi2026/adminlist.txt`, sibling to `cluster.ini`,
  `Master/`, `Caves/`) **[zip]**.
- Format: one Klei user ID per line, `KU_xxxxxxxx` for online-authenticated
  accounts (`OU_...` exists for offline-mode accounts, not relevant here
  since `offline_cluster = false`) **[doc, confirmed by both zip's real
  8-character-suffix `KU_` ID and multiple hosting KBs, e.g.
  [Nodecraft: Adding Admins](https://nodecraft.com/support/games/dont-starve-together/adding-admins-on-your-dont-starve-together-server)]**.
  A player finds their own ID in-game via console `TheNet:GetUserID()`, or
  an admin can read it off `server_chat_log.txt` after the player has said
  anything in chat **[doc/forum]**.
- Whether it matters here: **yes, worth carrying over per-world (or, more
  simply, cluster-wide since Tyler's friend group is fixed and small)**.
  Tyler's real cluster has exactly one admin entry (himself). Since the
  friend group is a fixed ~6-person allowlist already known to the webapp,
  **[inference, medium-high confidence]** the simplest design is: the
  webapp's existing allowlist IS the source of truth for `adminlist.txt`
  content (or a subset of it Tyler flags as admins), written into every new
  world's cluster directory by the same generator that writes
  `cluster.ini`. No new "who is an admin" UI is needed.

## 6. Architecture: dynamic registry vs hardcoded

**Smallest design that keeps the hardcoded registry working now while
leaving room to add "create world" later without rework** (all
**[inference]**, this is original design reasoning, not sourced):

- **World = an S3 prefix + a small manifest**, not just "an archive."
  ```
  s3://<bucket>/worlds/<world-id>/manifest.json
  s3://<bucket>/worlds/<world-id>/cluster.tar.zst   (or cluster/ prefix of loose files)
  ```
  `manifest.json` (minimal v1 shape, designed to be forward-compatible):
  ```json
  {
    "id": "tylerni2026",
    "displayName": "Tyler & Ni 2026",
    "hasCaves": true,
    "createdAt": "2026-09-19T00:00:00Z",
    "source": "seeded"
  }
  ```
  `source: "seeded" | "generated"` is the one field worth adding *now* even
  though nothing reads it yet — it costs nothing and means a future
  "created via UI" world is distinguishable from day one without a schema
  migration.

- **v1 (hardcoded registry) still works** by having the hardcoded list in
  code be literally `[{id: "tylerni2026", ...}]` — i.e. the Lambda/API's
  "list worlds" handler can read this from a static array *or* from
  `manifest.json` files under `worlds/*/manifest.json` with the same shape.
  If the API is written to read manifests from S3 from day one (even though
  today there's only one, seeded by hand alongside the zip's cluster
  contents), "add a world" and "create a world via UI" become the *same*
  code path later — just two different producers of a `manifest.json` +
  cluster prefix (a human running a seed script vs. a Lambda writing the
  template). **This is the single highest-leverage decision: make listing
  worlds an S3-manifest-scan (or a DynamoDB scan) from v1, even while there
  is exactly one hardcoded/seeded world.** Avoiding a truly hardcoded
  in-source array now is what makes "add create-world later" cheap; if v1
  ships with worlds truly hardcoded in Lambda source, migrating to dynamic
  listing is itself a small refactor later — cheap either way, but doing
  the manifest-scan from the start removes that refactor entirely.

- **A template cluster, generated by the API/Lambda**: "create world" =
  Lambda writes `cluster.ini`, `Master/server.ini`, `Caves/server.ini` (if
  `hasCaves`), `Master/leveldataoverride.lua`, `Caves/leveldataoverride.lua`,
  `adminlist.txt` to `s3://.../worlds/<id>/cluster/...` from the form inputs
  in §4, using the fixed port/`cluster_key` values from §1 (no per-world
  port allocation needed, confirmed by "only one world runs at a time").
  **No `save/` directory is written.** The EC2 instance's boot script
  already has to pull a cluster dir from S3 and run the server; "generate a
  new world" and "load an existing world" become the *same instance
  behavior* — the DST server itself decides, based on whether `save/`
  exists per shard, whether to generate or load (§2, §3 confirm this is the
  server's real behavior, not something the boot script needs to
  special-case). This is the key insight that makes "generate from UI"
  cheap: **the instance-side code needs zero new logic.** All new logic is
  on the API side (a form + a file-template writer).

- **What v1 must decide up front to keep this cheap later:**
  1. **ID scheme**: url-safe slug (e.g. lowercase kebab, `tylerni2026`) as
     the S3 prefix and manifest key. Decide this now; retrofitting IDs onto
     an existing prefix layout later is exactly the kind of migration this
     section is trying to avoid.
  2. **Manifest fields**: `id`, `displayName`, `hasCaves`, `createdAt`,
     `source` at minimum (above). Adding fields later is free (JSON);
     renaming/removing them is not — so avoid cute/ambiguous names now.
  3. **Where `cluster_password` comes from for new worlds**: decide
     **shared, not per-world**, and decide it now. Since only one world
     runs at a time and the friend group is fixed, a single cluster
     password (SSM SecureString, alongside the existing shared Klei token)
     applied to every world's `cluster.ini` at boot — analogous to how the
     token is injected — avoids a whole new secret-per-world storage and
     rotation problem. A "create world" form should therefore **not** ask
     for a password at all.
  4. **Per-world vs shared ports**: confirmed same for every world (§1) —
     nothing to decide, just don't build per-world port allocation.
  5. **Whether `adminlist.txt` is generated per-world or shared**: decide it
     mirrors the webapp's existing friend allowlist (§5) — avoids a second
     "who's an admin" concept.
  6. **`cluster_key`** (`[SHARD]`, Master/Caves auth): can be a fixed
     constant across all worlds (never leaves the instance) or generated
     per-world at write time — either is fine, but pick one now so the
     template writer isn't ambiguous later.

## 7. Effort estimate and recommendation

Extra work beyond v1 (hardcoded/seeded single world, "start" flow only) to
add "create a new world" in the UI:

- **API endpoint**: `POST /worlds` — validate form input, write
  `manifest.json` + cluster file templates to S3 under a fresh slug.
  Small-to-medium: mostly file templating (§1, §6), no new AWS primitives
  if S3-manifest listing was already adopted in v1 (§6).
- **Form**: name, description, max players, game mode dropdown, caves
  checkbox (§4). Small — 5 fields.
- **Validation of user-supplied strings that end up in an INI file —
  real injection risk, not hypothetical**: `cluster_name`,
  `cluster_description` (and Lua string fields in `leveldataoverride.lua`:
  `name`, `desc`) are attacker-controlled-ish (any of the 6 friends) text
  that gets written verbatim into `.ini`/`.lua` files the DST server
  parses. Concrete risks, **[inference, this is standard injection
  reasoning applied to the concrete file formats above, not sourced from a
  DST-specific writeup]**:
  - A literal newline in `cluster_name` breaks out of the `key = value`
    line into a new INI line, letting a "name" inject arbitrary
    `[SECTION]`/`key = value` pairs (e.g. flipping `pvp = true`, or
    injecting a bogus `[SHARD]` block). **Must strip/reject `\n`, `\r`, and
    probably `[`/`]` at line-start.**
  - A literal `"` or `\` or newline in a Lua string field (`name`, `desc`
    inside `leveldataoverride.lua`) breaks out of the Lua string literal,
    letting injected text become executable Lua inside the file the server
    `return`s and loads. **Must Lua-escape these fields properly (or just
    reject quotes/backslashes/newlines outright since this is a display
    name, not free text)** rather than naively string-interpolating.
  - Simplest safe approach: whitelist a narrow character set for `name` and
    `description` (letters, digits, spaces, basic punctuation), reject
    everything else, and length-cap them. This sidesteps both the INI and
    Lua injection classes without needing a real escaping library for two
    file formats.
- **Deletion/archival of worlds**: not free — needs an explicit "delete
  world" action (S3 prefix delete) and a decision on whether a world that's
  running can be deleted (probably: block delete while running, matching
  the "only one world at a time" constraint already in place).
- **S3 storage growth cap**: each world's cluster archive is ~tens of MB
  (compressed save + configs) per Tyler's zip (~9.3 MB compressed for one
  world with a season or so of play) — not itself alarming at 6 friends'
  worth of worlds, but unbounded "create world" with no delete UI means
  the registry only grows. Needs either a delete UI (above) or a soft cap
  (e.g. max N worlds, or a warning) — cheap to add, easy to forget.

**Recommendation: design-for now, build "create world" later (not v1).**
Rationale:
- Feasibility is high and the instance-side blast radius is genuinely zero
  (§6) — the DST server already does the generate-vs-load branching itself
  based on `save/` presence; nothing new needs to be taught to the EC2 boot
  script.
- But the *new* surface area is unglamorous, security-relevant text
  handling (INI/Lua injection, §7) plus lifecycle management (delete,
  storage cap) that has nothing to do with "does world generation work" and
  everything to do with hardening a form for even a small trusted
  friend-group. That's real effort disproportionate to a v1 whose stated
  goal is "get the existing world running on demand."
- The cheap, load-bearing thing to do **in v1** is exactly §6's "decide
  these six things now" list — especially **treat the world registry as an
  S3-manifest scan from day one**, even with only one seeded world. That
  one choice is what makes "create world" a pure additive feature later
  (new POST handler + form) instead of a registry-model migration.
